# International CV Export - Design Spec

Date: 2026-08-04
Status: Approved by owner, ready for planning

## Problem

The live terminal page (`Terminal.vue`) has print CSS, but it prints the terminal itself: dark-theme-flipped-to-print, same content and order regardless of who's reading it. It is not an ATS-safe traditional CV, and it has no concept of national CV conventions (photo, page length, section emphasis differ meaningfully between France, Switzerland, and the US). The only ATS-safe one-pager that exists today is a hand-made file in `_archives/CV_pdf/`, informed by `career-advisor.ts`'s writing guidance but never actually generated by the site.

career-advisor's report already told us to fix this (`docs/UPSKILLING.md`, suggested 2026-07-20), and the owner independently asked for the same thing, explicitly local-first and print-based (no PDF service).

## Scope

**In scope:**
- A new, dedicated `/cv` route rendering an ATS-safe traditional CV, separate from the terminal page.
- Three national templates: France, Switzerland, USA (the three template axes that differ most from each other: photo, page length, document label).
- Independent selection of template and language (EN/FR/DE) via URL query params, both explicitly re-selectable in the UI.
- A sensible default template inferred from the active language when `?template=` is absent, so a first-time visitor lands somewhere sensible without needing to touch a switcher.
- Browser-native print-to-PDF (`window.print()`), triggered by an explicit "Print / Save as PDF" button, not just the Ctrl+P shortcut.
- A reactive link from `Terminal.vue` to `/cv` carrying the current role and language.

**Explicitly out of scope (rejected during design, not deferred):**
- Server-side PDF generation (headless Chromium). Too much infrastructure weight (Docker image size, memory) for a personal site's occasional CV export; browser print already produces a real, savable PDF.
- IP-based geolocation to guess a visitor's country/template. Over-engineering for the actual problem: the template switcher already lets anyone reach any combination in one click, and the resulting URL (`/cv?role=...&lang=...&template=...`) is itself shareable, which solves the "share the right version with the right person" problem better than a guess ever could.
- A references/contacts section. `master_data`'s `recommendations` field is testimonial quotes, not reference contacts - forcing it into a formal "References" block (which is what Swiss CVs mean by that term) would misrepresent the data.
- Dynamic, job-offer-aware skill filtering (paste an offer, get a live-filtered list). That is what `career-advisor.ts` already does as a separate tool; doing it here too would mean either a runtime LLM call (breaking the project's documented "zero LLM calls at runtime" architecture) or a second, weaker keyword-matching implementation of the same idea.

## Architecture

**New pure logic in `packages/core/src/buildCv.ts`** (tested, no I/O):
- `CvTemplateId = "fr" | "ch" | "us"`
- `CV_TEMPLATES: Record<CvTemplateId, CvTemplateConfig>` - a plain data config, not branching code:

  | | France (`fr`) | Switzerland (`ch`) | USA (`us`) |
  |---|---|---|---|
  | `photo` | `false` | `true` | `false` |
  | `maxExperiences` | 4 | 5 (all) | 3 |
  | `maxHighlightsPerExperience` | 3 | 4 (all) | 2 |
  | `documentLabel` | "Curriculum Vitae" | "Curriculum Vitae" | "Resume" |

- `buildCvView(template: CvTemplateId, role: TargetRole, lang: Lang, data: Resume): CvView` wraps the existing `buildProfile(role, lang, data)` and applies the template config:
  - Experiences: reuse the existing `orderByRole` relevance ordering (already used for projects/experiences elsewhere), then slice to `maxExperiences`; each experience's `highlights` sliced to `maxHighlightsPerExperience`.
  - Skills: sort by `level` descending, then prefer skills whose `tags` overlap with a small role-relevance tag set (same spirit as `orderByRole`, not a new personalization system), capped at 15 (in practice a no-op today: `master_data` only has 8 skills total).
  - `photo`: `data.person.avatarUrl` included only if `template.photo` is true.
  - `documentLabel`: passed through for the component to render as the page heading.

  This is a static heuristic, not real page-height measurement (rejected as over-engineering). Like the existing hand-made PDF, the owner may need to eyeball the print preview and adjust the config numbers if a template still runs long - that is an acceptable, cheap manual step, not a bug.

**New route:** `apps/web/src/pages/cv.astro`, following the exact shape of `index.astro` (minimal head, theme-init script, meta tags using `person`/`title.en`, `<body><CvDocument client:only="vue" /></body>`). All query-param parsing happens client-side in the Vue component, matching how `Terminal.vue` already does it via `parseViewParams`.

**New param parser:** extend `apps/web/src/lib/params.ts` with `parseCvParams(search): { role, lang, template }`. Template resolution: if `?template=` is present and is one of `fr`/`ch`/`us`, use it as-is (explicit always wins). Otherwise, infer from the resolved `lang`: `fr -> fr`, `de -> ch`, `en -> us`. This is the "happy path" default the owner confirmed - it covers the common case for free, and the explicit switcher (not this heuristic) is what actually solves the real cross-cutting case (e.g. a Swiss recruiter reading in English who wants the Swiss template): one click on `TemplateSwitcher` changes the URL to `/cv?role=...&lang=en&template=ch`, which is then a stable, shareable, copy-pasteable link.

**New component `apps/web/src/components/CvDocument.vue`:** renders the `CvView` in ATS-safe markup - single column, no terminal aesthetic, its own scoped print styles (isolated from `global.css`'s terminal-oriented print rules). Includes:
  - The "Print / Save as PDF" button (marked `no-print`, calls `window.print()` directly), so a recruiter unfamiliar with Ctrl+P/Cmd+P has an obvious affordance.
  - A `TemplateSwitcher.vue` component, styled identically to the existing `LangSwitcher.vue` (button group, `mono`, active-state border/color via CSS vars, marked `no-print` internally like the existing switchers).
  - Existing `RoleSwitcher`/`LangSwitcher` reused as-is for the other two axes.

**Terminal.vue change:** a small reactive link near the existing contact icons, `` `/cv?role=${p.role.value}&lang=${p.lang.value}` ``, so a recruiter's current role/lang context carries over instead of resetting to defaults.

## Data flow

```
URL (?role=&lang=&template=)
  -> parseCvParams()                                  [apps/web/src/lib/params.ts]
  -> buildCvView(template, role, lang, data)           [packages/core/src/buildCv.ts]
       -> buildProfile(role, lang, data)                [existing, packages/core]
       -> template-specific trim (experiences/bullets/photo/label)
  -> CvDocument.vue renders CvView
  -> owner/recruiter clicks "Print / Save as PDF" -> window.print() -> browser's native PDF export
```

No new API endpoint, no new backend logic - this is entirely a web-app-side, build-time-safe feature (same "zero LLM calls at runtime" posture as the rest of the site).

## Testing

Following the project's existing convention (pure logic gets unit tests; thin Vue/Astro components do not have dedicated component test files - see `SectionBlock.vue`, `TelemetryBar.vue`):

- `packages/core/src/buildCv.test.ts`: `buildCvView` behavior per template (experience/bullet counts, photo inclusion/exclusion, skill ordering and cap, document label), using the same real `data/master_data.i18n.json` fixture already used by `buildProfile.test.ts`.
- `apps/web/src/lib/params.test.ts` (already exists, covering `parseViewParams`): add cases for `parseCvParams`'s template-inference-from-language fallback and explicit `?template=` override behavior.
- `CvDocument.vue`, `TemplateSwitcher.vue`, `cv.astro`: no dedicated test files (matches existing convention), verified instead via `bun run build` (Astro build succeeds, static route generated) and a live dev-server smoke check (each of the 9 template x language combinations renders without error, print preview looks reasonable) before shipping, the same verification bar used for `Terminal.vue`'s error-state work earlier this session.

## Risks / limitations (stated up front, not discovered later)

- The static experience/bullet-count heuristic can still overflow a page for some role/template combinations if content is unusually long; this needs a manual look at the print preview per template, not an automated guarantee.
- Browser print-to-PDF output varies slightly by browser (margins, font rendering) - acceptable for a personal site, would not be acceptable if this needed to be pixel-identical across all readers, which it does not.
- No analytics on which template/language combination gets used; if this is ever wanted, it would piggyback on `career_telemetry.jsonl` rather than adding new tracking infrastructure.
